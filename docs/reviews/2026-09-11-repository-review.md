### R1 — [P1] 백업 실패 후에도 원본 세이브를 삭제함

위치: `scripts/reset_progress.bat:53-56,64-68`.

세이브 `copy`와 레지스트리 `reg export`의 종료 코드를 확인하지 않고 바로 `del`/`reg delete`를 실행합니다. 백업 폴더 쓰기 권한 부족이나 디스크 공간 부족 상태에서 사용자가 초기화에 동의하면, 복구 가능한 사본 없이 원본을 삭제할 수 있습니다. 출력도 실제 실패 여부와 무관하게 백업 완료라고 표시합니다.

개선: 삭제에 앞서 필요한 백업을 모두 완료하고, 각 종료 코드·파일 존재·크기(가능하면 해시)를 검증합니다. 원래 없는 레지스트리 키와 백업 실패를 구분합니다. 하나라도 실패하면 원본을 보존하고 비정상 종료합니다.

검증: 정적 제어 흐름으로 확인. 실제 세이브/레지스트리 삭제는 실행하지 않았습니다. 수정 후 임시 데이터와 쓰기 불가능한 백업 경로로 실패 경로를 검사해야 합니다.

### R2 — [P1] AP 기능을 끄면 커스텀 플레이 기록도 저장되지 않음

위치: `muse dash test/Patches/Battle/UI/APModPatch.VictoryBanner.cs:41-52`.

`EnableAPMod=false`이면 `OnShowVictory` Postfix가 기록 저장 전에 반환합니다. `TrySaveCustomRecord`에서 호출하는 `CustomRecordStore.SaveResult`는 현재 유일한 제품 코드 호출 지점입니다. 따라서 AP 배너/정확도 기능을 끄는 설정이 커스텀 최고 점수와 플레이 횟수 저장까지 중단합니다. 가상 곡 기록은 게임 저장 직전에 제거되므로 원본 세이브가 이를 대신 보존하지도 않습니다.

개선: 결과 수집·저장 훅을 AP 배너와 분리하고, 해당 배틀의 결과 인스턴스를 안정적으로 확보합니다. AP 토글은 표시/판정 변경에만 적용합니다. `APModPatch.cs`의 정확도 Postfix에는 반대로 AP 토글이 없어 설정 설명과 실제 범위도 함께 정리해야 합니다.

검증: 설정 선언, 모든 `SaveResult` 참조, 세이브 정리 경로를 정적으로 대조했습니다. 수정 후 AP를 끈 상태로 커스텀 곡 완주 → record 파일 갱신을 확인해야 합니다.

### R3 — [P1] 플레이 도중 바뀐 BMS의 지문으로 이전 채보 결과를 저장함

위치: `muse dash test/Core/CustomRecordStore.cs:130,163-170`, `Core/ChartFingerprint.cs:41-59`.

배틀에서 사용한 채보의 지문을 세션에 고정하지 않고, 결과 저장 시 `ChartFingerprint.ForUid(uid)`로 현재 파일을 다시 읽습니다. A 채보로 시작한 뒤 편집기로 B 채보를 저장하면, A의 점수/노트 수가 B의 지문과 결합됩니다. `LoadResult` 역시 현재 채보를 기준으로 비교하므로 잘못 저장된 결과가 이후 정상 기록으로 통과합니다. 기존 B 기록이 있다면 A 결과와 병합될 수도 있습니다.

개선: 파싱한 내용과 지문을 한 묶음의 변경 불가능한 스냅샷으로 만들고, 실제 주입에 사용한 스냅샷·기록 키·난이도를 배틀 시작 시 고정합니다. 저장 시 현재 파일로 지문을 재계산하지 않습니다. 바뀐 채보별 기록 보존 정책도 명시합니다.

검증: 실제 `CustomRecordStore`, `ChartFingerprint`, `PlayRecordMerge` 소스를 링크한 격리 실행에서 확인했습니다. 게임/Discord 의존만 스텁으로 대체했습니다.

```text

```

2노트 채보의 결과를 4노트 채보로 교체 후 저장했는데 저장 지문이 새 채보와 일치했습니다.

### R4 — [P2] 파일 감시의 300ms 억제가 최종 저장 내용을 놓침

위치: `muse dash test/Patches/Hwa/HwaResourceManager.Watcher.cs:84-95`.

첫 이벤트를 즉시 처리하고 300ms 이내 후속 이벤트를 버립니다. 쓰기를 여러 번 수행하는 편집기에서는 첫 이벤트가 파일 완성 전에 발생할 수 있습니다. 첫 파싱이 실패하거나 부분 내용을 읽어도 마지막 완료 이벤트가 억제되면 최종 내용은 다시 로드되지 않습니다. 현재 구현은 마지막 변경 뒤에 실행하는 디바운스가 아닙니다.

개선: 마지막 변경 이후 조용한 시간이 지난 뒤 한 번 읽는 방식으로 바꾸고, 공유 위반·부분 쓰기에는 제한적인 재시도를 적용합니다. 같은 곡의 재로드를 직렬화하여 오래된 로드가 최신 캐시를 덮지 않도록 합니다.

검증: 실제 Watcher 이벤트 처리 메서드에 두 번 연속 이벤트를 전달했습니다. 첫 파일은 `TITLE first`, 두 번째 파일은 `TITLE completed`였습니다.

```text
disk=completed, cache=first, reloadCalls=1
```

실제 OS 이벤트 타이밍까지 시험한 것은 아니며, 이벤트를 받은 뒤의 억제 동작을 재현했습니다.

### R5 — [P2] BMS 삭제 후에도 이전 채보 캐시가 유지됨

개선: 실제 파일 삭제/경로 이동과 일시적인 읽기 실패를 구분합니다. 안정적으로 파일 부재가 확인되면 캐시를 무효화하고 다음 선택/배틀에서 폴백을 재결정합니다. 진행 중인 배틀은 R3의 스냅샷을 유지합니다.

## 추가 개선 및 확인 과제

- **미디어 자원 수명:** `HwaBattleMediaController.Lifecycle.cs`는 다음 주입과 `ResetState`에서 클립을 파괴한다고 설명하지만 실제로 `ResetState`는 참조를 null로 만들고 `previousInjected` 변수도 사용하지 않습니다. 반복 플레이의 네이티브 오디오 메모리를 측정하고 안전한 종료 시점에 소유 자원을 정리해야 합니다. 과거 승리 이벤트 도중 Destroy로 게임이 깨진 이력이 있으므로 그 위치에 단순히 Destroy를 복원하면 안 됩니다. ManagedHeap 로그만으로 네이티브 누수를 판단하지 않습니다.
- **오디오 참조 통일:** 주입은 기존 AudioSource도 사용하지만 Pause/Resume와 Sync는 이름이 `HwaBattleBgmSource`인 오브젝트를 찾습니다. 실제 주입 소스를 공통으로 사용하도록 정리하고 기존 게임 소스 재사용 경로의 일시정지·싱크를 확인해야 합니다.
- **기록 파일 내구성:** `CustomRecordStore.cs:172`에서 최종 파일에 직접 덮어씁니다. 임시 파일 작성·검증 후 원자적 교체와 백업을 도입하면 저장 도중 종료/쓰기 오류로 최고 기록이 잘리는 위험을 줄일 수 있습니다. 한 줄 JSON 등을 읽지 못하는 수동 파서도 표준 직렬화기로 교체하는 편이 유지보수에 유리합니다.
